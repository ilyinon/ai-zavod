# V1.0.6.1: Базовый Tool Runtime

## Цель

Агент получает факты из рабочей папки через инструменты и объясняет результат,
а не имитирует чтение файлов или запуск тестов. Первый подключённый сценарий:
«разберись, почему падают тесты». Он не запускает полный dev lifecycle и не
применяет изменения к исходникам.

## Пользовательский сценарий

1. Открыть чат с привязанным проектом и выбрать модель с поддержкой function calling.
2. Отметить разрешение диагностики над полем ввода. В нём указаны модель и endpoint,
   получающие содержимое прочитанных файлов и вывод проверок.
3. Отправить «разберись, почему падают тесты» или другой запрос анализа проекта.
4. Агент запрашивает файлы, поиск и разрешённые проверки. Пользователь видит журнал
   инструментов рядом с диффом; технические результаты раскрываются отдельно от чата.
5. Люмен отвечает по собранным фактам. Разрешение расходуется на один запрос,
   сбрасывается при смене чата, проекта или модели и не распространяется на workflow.

Без разрешения новый runtime не запускается. Backend проверяет, что разрешение
относится к фактически выбранной модели. Проект без подходящего агента для проверок
анализируется в рамках прав менеджера; права других профилей ему не выдаются.

## Контракт Runtime

Контекст формирует только backend: `projectId`, `taskId`, `agentId`, `agentName`,
`workflowRunId` (необязательный), абсолютная рабочая папка, tool profile, разрешённые
инструменты и пути чтения. Модель не может заменить эти поля аргументами инструмента.

Цикл: `Generate → tool_calls → проверка прав/аргументов → запись running →
выполнение → запись результата → role=tool с исходным tool_call_id → Generate`.
Несколько вызовов из одного ответа выполняются последовательно. Используется
OpenAI-compatible Chat Completions function calling, без извлечения команд из Markdown.
Tool-only ответ с `content: null` поддерживается. Streaming инструментов пока не включён.
Модель, не вызвавшая ни одного инструмента, не считается выполнившей диагностику.

Инструменты:

| Имя | Аргументы | Результат |
| --- | --- | --- |
| `list_files` | `path`, по умолчанию `.` | Разрешённые файлы рекурсивно |
| `read_file` | `path`, `offset` от 1, `limit` до 400 | UTF-8 текст с номерами строк |
| `search_files` | `query`, `path` | Буквальный поиск: путь, номер строки, совпадение |
| `run_check` | `command`, `path` | Статус, stdout/stderr, ошибка, exit code |

В первой версии `run_check` поддерживает `go test ./...`, `go vet ./...`,
`python3 -m pytest`, `.venv/bin/python -m pytest`. Команда дополнительно проверяется
существующими `checks` и `executionpolicy` с tool profile исполнителя. Python использует
существующее управление `.venv` и `requirements.txt`; системный Python для pytest
напрямую не запускается. Установка зависимостей может выполняться подготовкой `.venv`.
Произвольные команды, обход подтверждения и активные CTF-инструменты не добавлены.

## Права и ограничения

- Пользовательские allowlist используют имена инструментов. Старые стандартные
  текстовые контракты адаптируются только при точном совпадении с известным default.
  Отключённые агенты не получают инструменты. `read project context` даёт только чтение.
- Диагностика выбирает включённого тестировщика или разработчика с подходящим профилем
  проверок в текущей группе чата. Иначе используется менеджер с собственными правами.
  Используются soul и skills исполнителя, модель остаётся выбранной в чате.
- Файлы читаются через `os.Root`. Абсолютные пути, `..`, symlink и специальные файлы
  запрещены; deny-паттерны имеют приоритет над allow-паттернами.
- Исключаются `.git`, `.zavod`, `.venv`, `node_modules`, build/dist/cache, `.env*`,
  SSH-ключи и PEM/key-файлы. Это фильтр путей, а не гарантия отсутствия секретов
  в обычном исходном коде или тестовых логах. Передавать приватные проекты можно
  только доверенной модели. Содержимое инструментов считается недоверенными данными.
- Проверки выполняют код проекта с правами процесса приложения. Это не OS sandbox:
  тесты могут читать другие файлы, обращаться к сети и изменять окружение.
  Не запускать диагностику неизвестного проекта без изоляции окружения.
- По умолчанию: 12 вызовов, 180 секунд на цикл, 12 KiB текста результата на вызов,
  64 KiB суммарного текста результатов. После исчерпания бюджета разрешён только
  итоговый ответ по собранным данным. Результат помечается `truncated` при сокращении.
- Один файл до 1 MiB; поиск до 3000 посещённых записей и приблизительно 8 MiB
  прочитанного текста за вызов. Большие деревья требуют более узкого `path`.
- Ошибка аргументов или политики возвращается модели как `blocked`. Повторные ID,
  oversized batch, сбой провайдера, лимит времени или сбой аудита останавливают цикл.

## Хранение и UI

`tool_invocations` в SQLite хранит ID цикла/вызова, task/project/agent, аргументы,
статус, ограниченный результат, время начала и окончания. Запись `running` обязательна
до исполнения. Если запись не удалась, инструмент не запускается.

После отмены сохраняется `cancelled`, после перезапуска приложения незавершённые записи
становятся `interrupted`. Записи нельзя перепривязать к другому чату. Удаление чата
удаляет его журнал; переключение чата загружает только его последние 100 вызовов.
Результаты не копируются в сообщения чата и не считаются изменёнными файлами.

Поповер открывается наведением, фокусом или нажатием. Каждая строка раскрывает
вывод и exit code; Escape закрывает поповер. Позиция ограничена экраном.

## Проверка Приёмки

- Интеграционный тест с локальным HTTP mock провайдера: запрос чтения Go-теста,
  реальный `go test ./...` с намеренной ошибкой, передача ошибки модели и ответ.
- Отсутствие согласия или несовпадение модели не вызывает провайдер/tool runtime.
- Unit-тесты: schema, tool_call_id, tool-only response, лимиты, отмена, audit failure,
  запрещённые команды, пути, секретные имена, custom allowlist и disabled agents.
- SQLite-тест: изоляция, восстановление interrupted и cascade при удалении чата.
- Browser smoke: раскрытие вывода, desktop/mobile, модельное разрешение на один запрос,
  отсутствие журнала и разрешения в другом чате.

## За Границами Релиза

Интерактивный shell, PTY, потоковые логи процессов, полноценная OS-изоляция,
исполнение approvals, `apply_patch`, новый diff/rollback, перенос всех lifecycle-шагов
на tool loop и автономные CTF-команды относятся к следующим этапам V1.0.6.
