# Исправление V1.0.6.1: Intent Routing и надёжность Lifecycle

Статус: спецификация к реализации.

## 1. Цель

Завод должен отличать вопрос о программировании от поручения изменить проект.
Сбой LLM-провайдера не должен запускать исправление кода или бесконечные переходы
между агентами. Пользователь должен видеть действительную причину остановки и
одинаковый прогресс во всех частях интерфейса.

Основной сценарий приёмки:

> как написать сортировку пузырько в Go lang?

Ожидается прямой ответ Люмен на русском: объяснение и корректно оформленный
пример Go-кода. Без создания workflow, файлов, task blueprint, запуска проверок,
запроса рабочей папки и использования разрешения диагностики.

## 2. Подтверждённые Проблемы

- В `internal/router/router.go` проверка `hasCodingVerb` выполняется раньше проверки
  вопроса. В список маркеров действия включено `написать`. Информационный запрос
  получает `coding_task` и `confidence=high`, поэтому LLM-классификатор не вызывается.
- HTTP-клиент в `internal/providers/openaiapi/client.go` имеет таймаут 90 секунд.
  Ошибка ожидания HTTP-заголовков доказывает истечение клиентского таймаута, но
  не доказывает перегрузку модели или конкретную неисправность сети.
- Lifecycle разрешает возврат после исчерпания retry-бюджета. Переход через
  `ActionJump` удаляет результат целевого шага и может снова запустить его.
  Переход на самого себя не должен становиться обходом лимита повторов.
- `internal/lifecycleruntime/runner.go` при достижении общего лимита возвращает
  `lifecycle runtime reached max turns`, не включая первичную причину сбоя.
- В пользовательском примере одновременно отображались `3/5` и `5/8`.
  При реализации необходимо устранить независимый расчёт прогресса из
  динамического пользовательского плана и фиксированного dev lifecycle.

Точное количество сетевых попыток и причина недоступности Qwen в приведённом
запуске не установлены. Не выдавать предположения о сервере за результат диагностики.

## 3. Границы Изменения

Включено:

1. Семантическое различение объяснения, анализа и действия.
2. Уточнение неоднозначных поручений до запуска workflow.
3. Типизированные ошибки провайдера и ограниченные сетевые повторы.
4. Общий учёт повторного входа в шаг, включая циклические возвраты.
5. Сохранение причины остановки и понятные пользовательские статусы.
6. Единая проекция исполняемого плана в интерфейс.
7. Регрессионные и интеграционные тесты.

Не включено: новая модель, настройка сервера Qwen, увеличение всех таймаутов,
новый shell runner, изменение разрешений инструментов, реализация сортировки
в пользовательском проекте, переписывание всех legacy workflow.

## 4. Контракт Маршрутизации

### 4.1. Сначала намерение, затем предмет вопроса

Ключевое слово языка, алгоритма или ИБ-категории определяет тему, но не разрешает
действия. `написать`, `Go`, `Python`, `RCE` или `CTF` сами по себе не являются
основанием запускать исполнение.

Использовать существующие intent вместо параллельной системы типов:

| Намерение | Intent | Поведение |
| --- | --- | --- |
| Объяснение, обучение, пример в чате | `direct_answer` | Отвечает Люмен, инструментов нет |
| Анализ текущего проекта | `project_analysis` | Tool Runtime в пределах разрешений |
| Создание или изменение результата в проекте | `coding_task` | Dev workflow |
| Поиск актуальных внешних данных | `research_task` | Существующий research-путь |
| Практическая ИБ/CTF-задача | `pentest_task` | Профильная команда с проверкой scope |
| Управление существующим запуском | `workflow_control` | Только явно запрошенное действие |
| Ответ на конкретное ожидающее уточнение | `clarification_answer` | Продолжение связанного запроса |

`NeedsWorkflow`, `NeedsProjectContext` и `NeedsClarification` должны быть согласованы
с intent. Orchestrator не должен переводить информационный ответ в workflow только
из-за выбранной Dev-группы, привязанного проекта или предыдущей задачи разработки.

### 4.2. Правила разрешения неоднозначности

- «Как написать», «объясни», «покажи пример», «как работает» обычно означают ответ,
  а не изменение проекта. Анализировать фразу целиком, включая отрицания и дополнения.
- «Можешь исправить файл?» является поручением, несмотря на вопросительный знак.
  Нельзя исправлять роутер правилом «любой вопросительный знак = direct answer».
- «Покажи пример в чате, файлы не меняй» запрещает workflow с изменениями.
- Цитаты, блоки кода и вставленные логи с «напиши/исправь» не являются поручением.
- «Объясни и добавь в проект» разрешает действие. Ответ должен сохранить обе части
  запроса; одного вводного слова «объясни» недостаточно для direct answer.
- Короткое «реализуй это» может ссылаться на обсуждавшийся пример в том же чате.
  Историю использовать для восстановления объекта действия, но не для превращения
  нового самостоятельного вопроса в продолжение старого workflow.
- Активное уточнение не должно поглощать новый независимый вопрос. Продолжение
  связывается с ID ожидающего запроса; неясная ссылка требует уточнения.

### 4.3. Классификатор и безопасный fallback

Простые однозначные случаи решаются правилами без дополнительного LLM-запроса.
Конфликтующие признаки не получают `confidence=high`. Для них допустим существующий
LLM-классификатор с ограниченным контекстом текущего чата и структурированным ответом.

Классификатор должен возвращать intent, краткую причину и признак необходимости
уточнения. Объяснение сохраняется для аудита, но не выводится служебным JSON в чат.
Модель не получает инструменты и не выполняет задачу во время классификации.

Бюджет классификации: один вызов, максимум 15 секунд, без вложенных сетевых повторов.
При невалидном ответе или недоступности классификатора:

- очевидный информационный запрос остаётся прямым ответом;
- неоднозначное поручение получает короткое уточнение, без побочных эффектов;
- молчаливый переход в `coding_task` запрещён.

Пример уточнения: «Показать пример здесь или добавить реализацию в проект?»
Сохранить исходный запрос и выбранный ответ; не заставлять пользователя повторять
всю задачу. Не создавать lifecycle до выбора режима.

| Запрос | Ожидаемое поведение |

| «Как написать сортировку пузырьком на Go» | То же без вопросительного знака |

## 5. Ошибки Провайдера и Сетевые Повторы

### 5.1. Типизированная ошибка

Расширить контракт LLM-провайдера совместимым Go-типом ошибки с `Unwrap`.
Использовать `errors.Is/As`, а не поиск слов `timeout` в строке.

Минимальные поля: `kind`, `retryable`, `modelId`, `httpStatus` при наличии,
`attempt`, `maxAttempts`, `elapsedMs`, безопасное сообщение и исходная причина.
Конкретное имя типа может следовать существующему стилю пакета.

| Kind | Повторять автоматически | Маршрут |
| --- | --- | --- |
| `provider_timeout` | Да, в сетевом бюджете | Тот же LLM-вызов |
| `provider_unavailable` / HTTP 502, 503, 504 | Да, в сетевом бюджете | Тот же LLM-вызов |
| `provider_rate_limited` / HTTP 429 | Да, с учётом Retry-After и дедлайна | Тот же LLM-вызов |
| `provider_auth` / HTTP 401, 403 | Нет | Остановка: доступ к модели |
| `provider_invalid_request` / HTTP 400, 404 | Нет | Остановка: запрос или конфигурация |
| `provider_invalid_response` | Не как сетевой сбой | Явная ошибка протокола/формата |
| `cancelled` | Нет | Завершение отменой |
| `execution_deadline` | Нет | Завершение по общему дедлайну |

Остальные ошибки по умолчанию не retryable. Не каждый network error временный:
например, ошибка сертификата или некорректный URL требуют отдельного сообщения,
а не бесконечных повторов.

### 5.2. Единственный владелец retry

Сетевые повторы выполняет один общий механизм вокруг LLM-запроса. Lifecycle,
Tool Runtime и provider adapter не должны независимо перемножать попытки.

Дефолты для обычного LLM-вызова:

- максимум три попытки: первая и не более двух повторов;
- максимум 90 секунд на отдельную попытку;
- задержки перед повтором: 2 и 5 секунд; Retry-After учитывается, если помещается
  в оставшийся бюджет;
- максимум 180 секунд на логическую LLM-операцию вместе с ожиданиями;
- фактический дедлайн равен минимуму собственного бюджета и дедлайна вызывающего
  контекста. Попыток может быть меньше трёх, если время уже закончилось.

Согласовать нынешний 120-секундный контекст workflow-шага с этим контрактом явно;
не создавать новый `Background` для обхода отмены и не увеличивать дедлайн всего
Tool Runtime после каждого обращения к модели. Для классификации действует
отдельный короткий бюджет из раздела 4.3.

После исчерпания сетевого бюджета ошибка является терминальной для текущего запуска.
Она не попадает в code repair и не активирует `OnFailureStepKey`, предназначенный
для доработки результата агентом. Уже успешные шаги и применённые изменения сохраняются.

Повторяется только запрос к модели. Ранее исполненные инструменты, записи файлов
и команды повторно не исполняются автоматически. После частичного stream-ответа
не добавлять повторный текст к старому сообщению; для этого релиза безопасный
вариант: остановить stream с явной отметкой неполного ответа.

## 6. Бюджет Lifecycle

Разделить три понятия:

- `providerAttempt`: попытка HTTP/LLM-запроса;
- `stepExecutionCount`: фактическое выполнение обработчика шага;
- `transitionCount`: переход управляющего runtime.

Все счётчики относятся к конкретному `workflowRunId` и сохраняются между
автоматическими retry, возвратами и восстановлением запуска.

Правила:

1. Первое выполнение обработчика даёт `stepExecutionCount=1`.
2. Допустимо не более `1 + MaxRetries` выполнений шага за один запуск;
   при `CanRetry=false` допустимо только первое.
3. Повторный вход через `retry`, `jump`, `on_failure`, `on_success`, self-loop
   или цикл `A → B → A` проверяет и расходует тот же бюджет целевого шага.
4. Удаление устаревшего результата для повторного запуска не удаляет счётчики.
   Бюджет проверяется до исполнения обработчика, включая параллельные ветки.
5. Сетевые попытки внутри одного вызова обработчика не считаются code repair.
   Исчерпанный provider-бюджет завершает запуск без перехода к другому агенту.
6. `MaxRepairIterations` ограничивает число инициированных циклов доработки
   всего workflow; это дополнительное ограничение, а не замена лимита шага.
7. `MaxTotalIterations` остаётся общей защитой от циклов управляющих переходов.
   Увеличение значения не является исправлением логики retries.
8. Если последний допустимый обработчик достиг критериев завершения, runtime
   должен вернуть успех. Нельзя требовать ещё одну бюджетную итерацию только
   ради обнаружения `ActionComplete`.
9. `WaitHuman` и отмена не должны попадать в busy-loop. Возобновление после ответа
   пользователя сохраняет бюджеты и ID запуска.

В редакторе lifecycle пояснить семантику retries. Валидатор предупреждает о
циклических переходах, но не запрещает осмысленные ограниченные repair-циклы.

## 7. Причина Остановки и Поведение Чата

Хранить отдельно:

- последнюю ошибку попытки;
- актуальную первичную ошибку, приведшую к остановке;
- механизм остановки: provider budget, step budget, общий лимит, отмена, human gate.

Успешная последующая попытка закрывает старую ошибку: исторический сбой не делает
успешный запуск красным. При исчерпании общего лимита сохранять связанную ошибку
шага, если она есть; при чистом управляющем цикле сообщать именно о цикле.

Пример итогового сообщения:

> Не дождалась ответа Qwen на шаге «Реализация алгоритма».
> Сетевые попытки остановлены по лимиту времени. Ранее завершённые шаги сохранены.

Показывать фактические число попыток и длительность в раскрываемых деталях.
Не выводить `max turns` вместо причины и не предлагать уточнять ясную задачу,
если недоступна модель. Не утверждать, что сервер перегружен без подтверждения.

Состояния различаются по смыслу:

- повторный запрос к модели: «Повтор запроса к модели», номер попытки и ожидание;
- провайдер не ответил: «Не удалось получить ответ модели», запуск не выполняется;
- явный конфликт требований/отсутствующий секрет/scope: «Нужен ответ пользователя»;
- отмена: «Остановлено»;
- успешный запуск после retry: «Готово».

Предоставить повтор без повторного выполнения успешных шагов. Действие доступно
только для остановленного/ошибочного запуска и защищено от двойного нажатия.
Явный пользовательский повтор создаёт новый ID попытки продолжения с отдельным
бюджетом и ссылкой на исходный запуск; автоматический переход не может так
сбрасывать лимиты. Не переигрывать инструменты с побочными эффектами без проверки
их состояния. Если безопасное продолжение невозможно, объяснить это до запуска.

Сырые тела ошибок HTTP, Authorization, API keys, query-параметры с секретами
не должны попадать в пользовательский текст или телеметрию.

## 8. Единый План в Интерфейсе

Источником прогресса является сохранённый исполняемый план текущего запроса,
а не отдельно сгенерированный список обещаний модели. Публичные строки плана
сопоставляются с реальными шагами через стабильные step ID.

Backend отдаёт общую проекцию: `taskId`, `requestId`, `workflowRunId`,
`planRevision`, видимые шаги с ID, текущий step ID, статус и причину остановки.
Использовать существующие сущности плана, добавляя недостающие поля,
а не создавать второй независимый plan store.

- Верхняя панель, плашка над вводом и поповер используют одну проекцию.
- Если показано пять пользовательских шагов, оба индикатора показывают номер из пяти.
  Внутренние шаги допускаются, но не входят в публичный счётчик отдельно.
- Ветки и необязательные шаги отражаются как planned/skipped/active в этой же
  проекции; изменение состава обновляет `planRevision` для всех представлений.
- Повтор шага меняет его attempt, но не создаёт новый шаг в знаменателе.
- До определения intent допустим статус «Люмен разбирает запрос», без обещания `1/8`.
- Для direct answer нет активного dev-плана. История предыдущего workflow может
  оставаться доступной отдельно, но не изображает исполнение нового вопроса.
- Запоздалое событие другого чата, запроса или старой ревизии игнорируется.
- При остановке синхронно обновляются статус запуска, текущий шаг и статус агента.
  Агент не остаётся «в работе» после терминального события.

## 9. Совместимость и Миграции

Сохранить существующие intent и публичные поля ошибок для старых клиентов;
структурированную причину и счётчики добавлять совместимо. Старые завершённые
workflow не перезаписывать выдуманной точной причиной или количеством попыток.

Для старого незавершённого запуска восстановить счётчики из доступных записей
исполнения. Если история недостаточна, не продолжать автоматически с нулевым
бюджетом: показать состояние восстановления и предложить явный повтор.

Разрешение диагностики из V1.0.6.1 не является разрешением изменять файлы,
не определяет intent и не расширяет права агентов. Для общего вопроса чекбокс
не обязателен и не должен появляться как блокирующий запрос разрешения.

## 10. Порядок Реализации

1. **P0: Router.** Правила explain/action, контекст, fallback, таблица unit-тестов.
   Интеграционно доказать отсутствие workflow для исходного вопроса.
2. **P0: Ошибки провайдера.** Тип ошибки, единый retry, бюджет времени, отсутствие
   code repair на transport failure. Тесты с локальным HTTP mock и управляемыми часами.
3. **P0: Lifecycle.** Общий счётчик входов в шаг, self-loop и межшаговые циклы,
   корректное завершение на границе бюджета, сохранение причины ошибки.
4. **P1: Хранение и восстановление.** Совместимые поля, счётчики и безопасный
   пользовательский повтор; защита от дублей.
5. **P1: UI.** Одна проекция прогресса, понятные причины, ожидание retry и
   terminal-статусы. Обновить Wails bindings и frontend DTO.
6. **Приёмка.** Полный Go test suite, race-тесты изменённых конкурентных путей,
   frontend build, Playwright desktop/mobile и сборка macOS-приложения.

Основные места изменения: `internal/router`, `internal/orchestration`,
`internal/providers/openaiapi`, `internal/llm`, `internal/lifecycle`,
`internal/lifecycleruntime`, `internal/app/service.go`, `internal/store`,
`frontend/src/App.tsx`, `frontend/src/lib/backend.ts` и компоненты прогресса.

## 11. Критерии Готовности

- Исходный вопрос даёт один ответ Люмен с Go-примером. В нём сохраняются переводы
  строк и Markdown; отсутствуют утверждения о выполненных тестах или созданных файлах.
- Этот запрос одинаково работает без проекта, с Dev Squad, с другой выбранной
  группой и после ранее завершённого/ошибочного dev workflow.
- Для прямого вопроса не создаются workflow, blueprint, proposed changes, tool
  invocations или рабочая папка. Нет дополнительных LLM-вызовов планировщика и агентов.
- Все случаи таблицы маршрутизации покрыты тестами; явное поручение изменить код
  не превращается в объяснение из-за вопросительной формы.
- Mock timeout, 429, 503, 401, invalid response и отмена приводят к различимым
  результатам. Число HTTP-вызовов и время ограничены контрактом; ожидание Retry-After
  не выходит за дедлайн. Тесты не ждут настоящие 90/180 секунд.
- Transport failure не вызывает продукт, архитектора, разработчика или ревьюера
  для исправления кода и не повторяет уже исполненные инструменты.
- Self-loop, цикл `A → B → A` и параллельный повтор не обходят лимит шага.
  Перезапуск приложения и автоматическое продолжение не обнуляют бюджет.
- Успех на последней допустимой попытке отображается как успех, старые ошибки
  остаются только в истории. При остановке доступны первичная причина и механизм.
- Воспроизведение плана из пяти публичных шагов не показывает рядом `5/8`.
  Переключение чата и запоздалые события не меняют план текущего запроса.
- Пользовательский повтор не дублирует сообщение, успешные шаги или действия
  с побочными эффектами; новые бюджеты доступны только после явного действия.
- Нет новых ошибок в существующих Go-тестах, frontend build и browser smoke.
  Проверка на реальной Qwen проводится отдельно на публичном тестовом примере;
  её отсутствие не подменяется утверждением об успешном live-тесте.
